---
title: Composable apps cutover
description: Coordinated downtime for schema 39 to SQL40 and Go41
---

This is a downtime upgrade: stop all cluster writers, apply
[SQL40](https://github.com/omnara-ai/omnara/blob/main/migrations/000040_composable_apps.sql) and the frozen
[Go41 migration](https://github.com/omnara-ai/omnara/blob/main/migrations/000041_slack_app_cutover.go), then start the
matching release. SQL40 checks unfinished work, the exact continuation frontier
and custom/built-in name collisions **before any rename**; failure leaves schema
39 usable by the old release. Go41 repeats those checks under its config rewrite
lock. The two migrations commit separately: **a later Go41 failure leaves schema
40 applied; the old API, worker and maintenance must stay stopped.**

Inventory your deployment before scheduling. Set the window from a restored-copy
rehearsal with the exact release artifacts, allowing time for recovery. Local
fixture tests establish neither production readiness nor a fixed completion time.

## What changes

- Installs become connections with the same identities and credential references.
  SQL40 captures each old Slack setup as a project app. Keep the existing Slack
  app, tokens, secret encryption keys, public origins and callback URLs.
- Agents, historical events, attribution and Slack messages survive. Go41 renames
  stored tool policies (`send_integration_message` to `slack_post_message`,
  `set_integration_target` to `set_interaction_destination`), including historical
  configs; it does not rewrite message text.
- Eligible old agents get individual compiled-only successor configs containing
  their own Slack send scopes and existing explicit tool policy. Shared profiles
  do not acquire those destinations. Archived agents, subagents and agents with
  no previous turn are included when their org/project, target and connection
  meet Go41's selection. Disabled connections remain subject to live revocation.
- Old conversations get **no listeners, follow policy or interaction handler**.
  Old automatic interaction destinations are cleared. Plain replies in an old
  thread do not resume its previous agent; a fresh mention can launch a new one.
  Cancel old pending turns/prompts before migrating; resume an old agent through
  the dashboard/API, or attach new receiving/handler capabilities explicitly.

## API and configuration changes

This release replaces the project `/integration-installs` collection and item
routes with `/integration-connections`; there is no old-route alias. Existing
`iin_` identifiers remain valid. Upgrade API clients and generated SDKs with the
cluster release. Connections describe provider accounts and credentials; their
old `agent_profile_id`, `agent_id`, `integration_kind` and `connection_mode`
fields are removed. Configure launch behavior through [project apps](/integrations/apps).

Actor responses can now report `github` and `discord` providers, and secret
responses can report the `github_app_credentials` kind. Update clients that
validate these response values as closed enums before enabling the new providers.

The migration rewrites stored configurations, but clients that submit new source
must use `slack_post_message` and `set_interaction_destination` instead of the
removed generic tool names. Slack access now requires an explicit app resource;
a tool name alone grants no access. Existing Slack OAuth, event and interaction
callback URLs are preserved, so this API rename requires no Slack webhook change.

## Prepare and rehearse

1. Pin the release images for `api`, `worker`, `maintenance`, `web` and `migrate`;
   retain the old images and configuration for a restore. Use the existing
   [deployment procedure](/self-hosting/deployment), [Compose file](https://github.com/omnara-ai/omnara/blob/main/compose.yaml)
   and [cluster release workflow](https://github.com/omnara-ai/omnara/blob/main/.github/workflows/cluster-release.yaml).
   The workflow publishes images; map the shutdown/startup steps below to the
   actual deployment's replica and scheduler controls before the window.
2. Confirm the starting schema is 39 on the PostgreSQL writer. Inventory every
   gate below with read-only queries during preparation, retaining the queries
   for an identical check after the freeze. Retain IDs/counts and logs, not
   credentials or config/prompt bodies. Successful query execution alone does
   not certify a gate: review its results.
3. On an isolated restored copy, rehearse old-release cancellation, the writer
   freeze, both migrations, validation and **snapshot restoration** with the exact
   release artifacts. Keep provider egress disabled or use an authorized test
   workspace. Verify backup completeness, restore access and the existing secret
   key ring/blob storage references. Read-only SQL cannot validate YAML,
   config hashes, rewritten-config uniqueness or runtime decoding; Go41 and the
   restored-copy checks must succeed too. Repair historical custom-name
   collisions before the window through a reviewed migration/repair; merely
   changing a current profile leaves the historical blocker intact.
4. Leave config quota room for at most one successor per eligible agent, counting
   **all** stored configs, plus capacity for subsequent app launches. This release
   raises the default to 10 million configs per project; explicit org overrides
   still take precedence. Review any existing
   `max_agent_configs_per_project` org override if necessary; do not
   delete config history to make room. Inventory OAuth/setup flows and old
   interactive callbacks for smoke tests. Record intended backlog and schedule
   disposition so restarting workers does not unexpectedly resume work.

Use a read-only transaction on the explicitly selected writer for the inventory:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT current_database(), pg_is_in_recovery(),
       max(version_id) FILTER (WHERE is_applied) AS applied_version
FROM goose_db_version;
-- Require the intended database, pg_is_in_recovery = false, version = 39.
-- Run the reviewed SELECT queries for every gate below in this snapshot.
ROLLBACK;
```

| Gate | Required result before SQL40 |
| --- | --- |
| Raw work, across the whole database | No `agent_runtime_locks` with `lease_expires_at > statement_timestamp()`, no `model_call_contexts.state = 'started'`, no `tool_calls.state <> 'completed'`, no `agent_interactions.state = 'open'`. SQL40 checks before renaming; Go41 rechecks under lock. |
| Derived work, for every agent with a latest turn | No `agent_continuable_model_contexts` or `agent_next_model_work` row for that latest turn (greatest `agent_turns.turn_sequence`), and `agent_has_incomplete_tool_batch(project_id, agent_id)` is false. Pass the same project/agent IDs to both frontier functions. An idle worker is insufficient. Historical failed/retry contexts superseded by success or stop are not themselves blockers. |
| Stored configs | No `compiled_definition.tools` entry of type `custom` named `slack_read`, `slack_post_message`, `github_read`, `github_discussion_comment`, `github_inline_comment`, `github_reply`, `discord_read`, `discord_post_message`, `list_interaction_destinations` or `set_interaction_destination`; no unequal old/new policy pair in definition, compiled definition or source for either rename above. Check historical as well as current configs. Only the name-collision guard runs before SQL40's rename; Go41 also checks policy conflicts, source parsing/hashes and rewrite uniqueness. |
| Old setup and addresses | Every install, including deleted rows, satisfies SQL40's Slack / `agent_profile` / `webhook` gate. Eligible targets use `dm` or `channel` with `^[CDG][A-Z0-9]+$`, or `thread` with that channel plus `:` and `^[0-9]+\.[0-9]+$` timestamp. No eligible current compiled config already has `app_resources`. |
| Quota and writer freeze | `effective_resource_limits.max_agent_configs_per_project` minus all stored project configs minus the number of eligible agents must be nonnegative, with further launch capacity planned; every writer stopped and the same preflight rerun after the freeze. Database sessions alone cannot prove the freeze. |

Eligible agents have a current config, an undeleted org/project, and an undeleted
Slack target/connection. Do not exclude archived agents, subagents, agents with
no previous turn or disabled connections. Count each eligible agent once for
quota, even when it has several targets. SQL40/Go41 are the final gates; do not
bypass their checks if preparation missed a blocker.

The [39 → 40 → 41 fixture test](https://github.com/omnara-ai/omnara/blob/main/internal/dbmigrate/slack_app_cutover_integration_test.go)
checks scoped successors, historical config reads, strict runtime decoding, no
listeners or new runnable work, and later public input. A real continuable retry
fails at **39**; historical failures superseded by success/stop are allowed. An
injected Go41 failure leaves **40**, and rerunning succeeds after the injected
cause is removed. This is not a snapshot-restore test or live Slack rehearsal.
Run against the final release code using local test services:

```sh
# Local test services only; defaults are documented in Makefile.
make db-up
go test -count=1 ./migrations -run '^TestSlack'
OMNARA_TEST_DATABASE_URL='postgres://omnara:omnara@127.0.0.1:55432/omnara?sslmode=disable' \
  go test -race -count=1 -tags=integration ./internal/dbmigrate \
  -run '^TestSlackAppCutoverPreservesScopedSendingAndHistory$'
```

## Announce, cancel and freeze

1. **About one hour before:** enable the Cloudflare announcement banner with the
   date, window and timezone. Use the packaged
   [Cloudflare snippet](/self-hosting/assets/cloudflare-maintenance.mjs), also at
   `docs/self-hosting/assets/cloudflare-maintenance.mjs` in the release checkout.
   Set `NOTICE`, then use `MODE = "banner"`, `"maintenance"`, and `"off"` for the
   three stages via [Cloudflare Snippets](https://developers.cloudflare.com/rules/snippets/create-dashboard/).
   Scope its rule to the app, public API and webhook hostnames. Preview the rule
   before enabling it; the file defaults to off. The banner appears on fresh
   navigation/refresh.
2. **At cutover:** enable full maintenance. Verify browser responses and POSTs
   to `/api/integrations/slack/events` and `/api/integrations/slack/actions` return
   **503**, with non-browser failures rather than HTML 200. Preserve the OAuth
   callback `/api/integrations/oauth/callback` and both Slack URLs. Block direct
   origin/public ingress too, retaining only restricted operator access. The
   snippet does not close existing connections or stop internal writers.
3. Disable scheduled cron triggers through the old API, recording which to
   re-enable; pause external input producers, automation and automatic
   restarts/rollouts. Cron firing runs inside the worker; blocking ingress does
   not pause it. While the **old** API and required execution/recovery services
   remain available privately, cancel outstanding turns and interactions through
   their normal lifecycle. Use the old dashboard Cancel action or
   `POST /api/v1/orgs/{orgID}/projects/{projectID}/agents/{agentID}/cancel`
   (adjust the versioned API mount for your deployment), with public IDs and
   normal authorization. See [agent cancellation](/agents/overview#stop-current-work)
   and [cancellation implementation](https://github.com/omnara-ai/omnara/blob/main/internal/storage/executionstore/agent_runtime_cancellation_store.go).
   Cancellation supplies neither approval nor an answer, and closes the same
   interaction shown in the dashboard. Do not archive agents or edit terminal
   states with SQL. Go41's gates are global: clear all reported work, not only
   agents with a currently selected Slack target.
4. Confirm cancellation settled, including tool results and runtime release.
   `runtime_cancel_requested` is not proof of drain. CancelAgent preserves queued
   backlog; cancel unwanted queued inputs through the old API, or deliberately
   retain them for reopening while preventing readmission during drain. Let the
   old release finish recovery and best-effort Slack prompt dismissal. If any
   gate remains blocked, resolve it while still on schema 39 or postpone.
5. Gracefully stop **every replica** of old worker, maintenance and API, plus web
   and any other service/job with database or admission access; close existing
   sockets and prevent replacements. The maintenance service is a writer too.
   Keep Postgres, Redis and blob storage available. `omnarad` upgrades separately:
   this cutover introduces no daemon protocol upgrade requirement. It writes
   through the API, not directly to Postgres. Stopping the API fences its control
   plane writes; machine runtimes are distinct from the agent runtime locks in
   the gate. Existing detached machine processes may continue, so coordinate
   their external activity if needed rather than assuming a cluster stop kills
   them or deleting daemon state.
6. **Rerun the identical read-only preflight now, after the freeze.** All blocker
   sections must be empty and headroom reviewed. Capture the final schema-39
   snapshot/backup and verify its restore procedure before applying SQL40.

Maintenance responses do not queue requests. Provider retry windows are limited;
Slack documents bounded [Events API retries](https://docs.slack.dev/apis/events-api/#retries).
A message or action sent during downtime may need to be resent after reopening.
`Retry-After` is not a delivery guarantee; the new inbox only protects receipts
actually persisted by the new service.

## Migrate, validate and reopen

1. Keep maintenance and the writer freeze in place. Run the release's one-shot
   `migrate` image, which invokes [cmd/migrate](https://github.com/omnara-ai/omnara/blob/main/cmd/migrate/main.go) with the
   [registered Go migrations](https://github.com/omnara-ai/omnara/blob/main/migrations/go_migrations.go). Use the direct
   PostgreSQL writer, not RDS Proxy or transaction-pooling PgBouncer. Configure
   `OMNARA_DATABASE_URL`, `OMNARA_MIGRATIONS_DIR` and
   `OMNARA_MIGRATION_TIMEOUT` as in
   [database configuration](/self-hosting/configuration#database-and-redis).
   Do not use a plain SQL-only Goose invocation: Go41 must execute. Capture exit
   status and complete logs; start no service between 40 and 41.
2. Require successful completion through 41 and check the migration version on
   the writer. Before starting writers, compare the rehearsal/backup inventory:
   existing agents/history/targets and credential references remain; Slack app
   setup has encoded connection references; eligible agents have isolated
   successor scopes and preserved explicit policy; old pointers are cleared and
   no old-thread listeners were created. Inspect metadata/IDs, not secret values.
   Use the fixture assertions above as the acceptance checklist.
3. Start only the matching new cluster images behind maintenance, keeping
   schedules and normal inputs paused until checks finish. **Starting workers can
   consume retained backlog even with ingress blocked.** If customer work must
   remain frozen, validate execution/provider journeys in the isolated rehearsal
   and defer worker startup until reopening; do not assume a global claim-pause
   switch. Validate private
   service health, historical agent/config reads, dashboard cancellation state
   and normal input on a test agent. In an authorized test Slack workspace,
   verify mention → new agent → reply continuation, scoped sending, and a new
   question/approval resolved through Slack and dashboard. Check an old canceled
   button cannot resolve a new interaction; old plain replies must not resume
   their previous agents. Permit only controlled test ingress for these checks;
   do not reopen all provider callbacks as a test bypass.
4. Record the decision to reopen, then disable maintenance and restore intended
   schedules/admissions. Monitor migration/service errors, failed receipts and
   pending receipt age. Explain the old-thread reset and resend requirement to
   users. A startup or smoke failure keeps maintenance active.

## Recover failed app events

Use the matching release's `maintenance` binary with `OMNARA_DATABASE_URL` set
to the intended deployment database. These operator commands do not start the
maintenance loops or require Redis. Replace the project public ID and use the
receipt UUID returned by `list`:

```sh
maintenance inbox list --project proj_... --state failed --limit 50
maintenance inbox show --project proj_... --receipt RECEIPT_UUID
maintenance inbox retry --project proj_... --receipt RECEIPT_UUID
maintenance inbox discard --project proj_... --receipt RECEIPT_UUID --reason "operator explanation"
```

Inspect the failure before choosing retry or discard. Output contains metadata,
frozen identities and progress flags, without provider payloads or credentials.
Retry requires a failed receipt and an active connection. It grants another
bounded attempt budget while preserving the original recipients, planned IDs,
prepared files and committed inputs; admission still checks current authority.

Discard releases a failed launch reservation only when no launch slot committed
and no selection target remains, including retired targets. Committed inputs to
existing agents do not block discard and retain their deduplication. A partially
launched selection must be retried. Discard works on disabled live connections.
The original receipt, plan and diagnostics remain stored; a new event can select
fresh launch membership. Completed and discarded receipts become eligible for
cleanup seven days after completion or discard. Transport deduplication lasts
until deletion; failed receipts remain available under live or disabled scopes.

After discard commits, prepared-file cleanup uses the existing blob settings
only when `OMNARA_BLOB_S3_BUCKET` is configured. Missing configuration or deletion
failure produces a warning when cleanup is needed; discard remains successful.
Repeat `discard` on the retained discarded receipt to retry cleanup without
changing its plan or retention timestamp. Committed inputs and durable artifact
references are protected. See the detailed
[operator recovery runbook](https://github.com/omnara-ai/omnara/blob/main/internal/storage/integrationstore/inbox_retention.md#operator-recovery)
for pagination, deadlines and cleanup limits.

These commands recover receipts already stored by Omnara. If a GitHub webhook
failed before intake persisted it, first restore intake and then manually
redeliver the failed delivery from GitHub. GitHub does not automatically retry
it, and Omnara has no GitHub redelivery scheduler. See
[GitHub delivery recovery](/integrations/github#configure-incoming-pr-work).

## Failure and restore

| Failure point | Recovery while maintenance remains active |
| --- | --- |
| Before SQL40, or SQL40 failed and version is still 39 | Its early work/frontier/custom-name guards leave the old schema usable. Resolve work using the old release privately; obtain reviewed historical-config repair for collisions, or postpone. Confirm the actual version and old-release health before reopening. |
| Go41 failed; version is 40 | Go-only hash, address, policy-conflict or quota checks can still fail after SQL40 commits; the repeated work guards can also catch a broken freeze. Go41 rolls back its own rewrites/successors. **Never restart old services on schema 40.** Preserve diagnostics; use a reviewed schema-40 SQL repair and rerun the same release migrator, or restore the pre-40 snapshot and old release. Do not copy the test's synthetic retry/trigger manipulation into operations. |
| Version 41, validation fails before customer traffic | Keep ingress blocked; stop all newly started writers. Use reviewed forward repair, or restore the pre-40 snapshot and old images/configuration. Account for any controlled smoke-test side effects: restoring Postgres does not unsend a Slack message or undo a machine command. |
| Customer traffic or retained customer work has resumed | Prefer forward repair. Restoring the old snapshot loses post-snapshot work and requires a separate, explicit recovery decision and reconciliation. |

Rollback means **restore the verified schema-39 snapshot**, point the stopped
deployment at the restored database with its matching keys/blob references, then
start and privately validate the old images before reopening. SQL40/Go41 are
forward-only; Goose down, deleting migration-version rows or merely rolling back
images is not a restore. The freeze and 503 responses stay in place throughout
repair or restore, including any repeat preflight and migration attempt.
