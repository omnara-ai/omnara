Self-hosting means running four core long-lived Omnara services plus a one-shot migration job, pointed at your own Postgres, Redis, and S3-compatible bucket ([Architecture](/self-hosting/architecture)), with one public URL in front of them. Deployments that enable managed messaging integrations also run the independently scalable `channel-gateway` service.

## Quick start (local)

The repository's compose file runs everything behind the `app` profile:

```sh
git clone https://github.com/omnara-ai/omnara && cd omnara
docker compose --profile app up -d --build
```

That builds from source (a checkout auto-loads `compose.override.yaml`). To run published release images instead, use the base file alone, optionally pinning a release with `OMNARA_RELEASE`:

```sh
docker compose -f compose.yaml --profile app up -d
```

Open `http://localhost:8000` and sign up — the local email driver is `console`, so the verification link will appear in `docker compose logs api`.

The optional `channels` Compose profile adds the Slack, Discord, and GitHub gateway. Configure the same connector token on API, worker, and gateway, and set the worker's full private `operations_url` in [connector configuration](/self-hosting/configuration#channel-gateway). The gateway needs writable temporary storage sized for its operation byte budget. The built-in registry includes all three providers. Configure their exact capabilities and Redis connection, then register and connect the provider apps in Omnara.

Slack setup, OAuth, and message intake requiring gateway processing return HTTP 503
until the API has the exact `omnara`/`slack` capability configured. This is a
configuration check, not a gateway health probe: normal temporary gateway outages
still buffer verified events in the durable inbox. The gateway receives only the
Slack access token; signing and OAuth client credentials stay in core.

Once those are configured, enable both the core stack and the optional gateway:

```sh
docker compose --profile app --profile channels up -d --build
```

## Production database upgrades

Run the release's one-shot `migrate` image before starting its API, worker, and
maintenance services. Connect the migrator directly to the PostgreSQL writer;
do not use RDS Proxy or transaction-pooling PgBouncer. Long-running services
may use a compatible proxy. See [database configuration](/self-hosting/configuration#database-and-redis)
for connection-pool defaults.

### Channel toolkit cutover

Rehearse this offline upgrade on a backup before scheduling the maintenance window.
The schema cutover is `000038_integration_channels.sql`, followed by
`000039_migrate_channel_tool_configs.go`. Preserve existing Slack apps, tokens,
conversation links, and OAuth setup links; this procedure does not reset them.

Before applying either migration, cancel outstanding legacy Slack approvals and
questions through the old API. Their dashboard copies are the same interactions
and close too; cancellation grants no permission and supplies no answer.

1. Pause public/provider ingress, scheduled work, workers, maintenance, and other
   execution writers. Keep only authenticated administrative access to the old
   API while preparing the cutover. Inventory open interactions on agents with
   legacy Slack associations, including disconnected target history. Save IDs
   and counts rather than prompt bodies or credentials. Do not infer a prompt's
   destination from the agent's mutable current channel.
2. For each selected agent, verify that every open interaction in its current
   continuable turn belongs in the cancellation scope. The steering operation
   cancels current-turn prompts as a group. If the inventory includes unrelated
   dashboard-only work, mixed scope, or prompts outside that turn, stop and resolve
   the scope. Do not substitute whole-agent cancellation or direct SQL updates.
3. Submit the following body to
   `POST /api/v1/orgs/{orgID}/projects/{projectID}/agents/{agentID}/inputs`, using
   public IDs and normal project authorization. Use a stable per-agent
   `Idempotency-Key`, such as `slack-channel-cutover:<batch_id>:<agent_public_id>`.

   ```json
   {
     "content_blocks": [
       {
         "type": "text",
         "text": "Pending Slack approvals and questions were canceled for the integration upgrade. No permission was granted and no answer was supplied. Ask again if still needed."
       }
     ],
     "delivery_mode": "steering",
     "cancel_open_interactions": true
   }
   ```

   Keep the key, body, and actor identical on retries, including after an ambiguous
   timeout. A replay does not cancel newly created prompts. If old execution resumes
   after an aborted cutover, inventory again and use a new batch for new cancellations.

4. Verify that each selected interaction is canceled, its parent tool call has a
   durable canceled result/event, and unrelated tools/interactions remain unchanged.
   Re-inventory while ingress and execution are still paused; no selected Slack
   prompt may remain open. Then stop the remaining API and establish the final
   backup/recovery point before applying the migrations. Old Slack buttons may
   remain visible, but they cannot authorize canceled requests.

Also inventory saved custom tools whose names collide with `list_channels`,
`get_channel`, `read_channel`, `set_current_channel`, or `send_channel_message`.
Check historical configs, including disabled tools: unfinished contexts can still
reference them. These formerly valid custom names now conflict with builtins.
Resolve any observed collision explicitly before upgrading; the config migration
does not rename or delete custom tools.

With all application writers stopped, `000039_migrate_channel_tool_configs.go` removes
only the retired builtin declarations `send_integration_message` and
`set_integration_target` from saved config source, definition, and compiled JSON,
and recomputes the source and effective-definition hashes. Config IDs and all
references remain unchanged. Historical config views intentionally show the
migrated definitions. The five replacement channel tools derive from live
bindings, not saved config declarations.

YAML and JSON source formatting may normalize during migration. Non-retired
values retain their meaning, and YAML comments are retained; source bytes are
not preserved exactly.

Recorded tool calls, arguments, and results remain unchanged. Unfinished ordinary
tools can still reconstruct their pinned config; pending calls to the two retired
tools are unsupported. There are no runtime aliases or historical fallback reader.

Like `000026_migrate_agent_config_names.go`, this is a one-time transactional
exception to config immutability: the config trigger is disabled for the updates and restored in the
same transaction. Existing uniqueness constraints remain enforced. If configs
converge on a duplicate, `000039_migrate_channel_tool_configs.go`'s updates and trigger
changes roll back. Goose commits each migration separately:
`000038_integration_channels.sql` remains applied. Do not restart the old release
against that incompatible schema. Keep services stopped while repairing the
observed duplicates and retrying the new
release's migrator, or restore the entire pre-upgrade backup before reopening
services. Rehearse this boundary before upgrading. The migration does not merge
configs, repoint references, or implement automatic duplicate repair.

## Exposing the deployment publicly

`OMNARA_PUBLIC_URL` is the public app origin used for email links, OAuth callbacks, and browser flows. The API defaults to the same deployment at `/api/v1`; set `OMNARA_PUBLIC_API_URL` when it is exposed at a different public URL. The daemon installer is served from the API origin at `/install/omnarad.sh`. These features will not function unless the configured URLs are publicly accessible.

Slack uses the event and action URLs returned by setup under `/api/integrations/slack/*`; route these to `api` along with OAuth callbacks. Core verifies and durably records accepted events before acknowledging Slack, and the channel gateway consumes the receipts over the private API.

The generic `/hooks/<integration-app>/<provider>/...` prefix routes to `channel-gateway` for explicitly registered webhook factories. Keep `/api/v1/channel-connector/*` and the gateway's `/internal/operations` endpoint private. The included nginx configuration blocks both at the public edge. The worker's `operations_url` should use the private service address, such as `http://channel-gateway:8080/internal/operations`. Set `OMNARA_CHANNEL_GATEWAY_PUBLIC_URL` to the exact public origin used to reconstruct provider webhook URLs.

<Warning>
  Set `OMNARA_PUBLIC_URL` on every backend service, and set
  `OMNARA_PUBLIC_API_URL` consistently on API, worker, and maintenance when
  using a separate API URL. Outside local development the public origin is
  required.
</Warning>

### Cloudflare Tunnel

One easy option to expose Omnara publicly is via a [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/).

#### Persistent Tunnel (recommended)

For a stable origin, add a domain to Cloudflare and create a named tunnel:

```sh
brew install cloudflared   # or see Cloudflare's install docs
cloudflared tunnel login
cloudflared tunnel create omnara
cloudflared tunnel route dns omnara omnara.example.com # replace with your preferred domain
cloudflared tunnel run --url http://localhost:8000 omnara
```

Then, restart the stack pointed at the tunnel's URL:

```sh
OMNARA_PUBLIC_URL=https://omnara.example.com docker compose --profile app up -d
```

`cloudflared service install` will keep a named tunnel running across reboots. Any other reverse proxy or tunnel (Caddy, nginx, Tailscale Funnel, ngrok) works the same way, as long as it forwards the public `Host` header — the API rejects hosts it doesn't recognize.

#### Quick Tunnel

For a temporary tunnel without a separate domain, you can use:

```sh
cloudflared tunnel --url http://localhost:8000
```

This prints a random `https://{subdomain}.trycloudflare.com` URL that changes every run. After starting the tunnel you can set `OMNARA_PUBLIC_URL` in the same way described above.
