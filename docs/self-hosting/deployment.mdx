Self-hosting means running four long-lived Omnara services plus a one-shot migration job, pointed at your own Postgres, Redis, and S3-compatible bucket ([Architecture](/self-hosting/architecture)), with one public URL in front of them.

## Quick start (local)

The repository's compose file runs everything behind the `app` profile:

```sh
git clone https://github.com/omnara-ai/omnara && cd omnara
docker compose --profile app up -d --build
```

That builds from source (a checkout auto-loads `compose.override.yaml`). To run published release images instead, use the base file alone, optionally pinning a release with `OMNARA_RELEASE`:

```sh
docker compose -f compose.yaml --profile app up -d
```

Open `http://localhost:8000` and sign up — the local email driver is `console`, so the verification link will appear in `docker compose logs api`.

## Production database upgrades

Run the release's one-shot `migrate` image successfully before starting the
matching API, worker, and maintenance binaries. The migrator requires a direct
PostgreSQL writer connection: use the RDS writer endpoint, a Kubernetes Service
that reaches the primary, or the equivalent direct primary endpoint on another
platform. Do not send migrations through RDS Proxy or a transaction-pooling
PgBouncer endpoint. Migrations rely on a session-level advisory lock and
session-scoped timeouts, while transaction poolers are free to switch the
underlying session.

Long-running services may use a compatible database proxy. Keep each service's
pgxpool limits aligned with the proxy and database connection budgets; see the
[database configuration](/self-hosting/configuration#database-and-redis).

Treat successful completion of the matching migration image as a deployment
precondition for the API, worker, and maintenance processes. Runtime readiness
checks database connectivity; it does not replace migration ordering. An older
migration binary still refuses to run against a database newer than its own
migration set, preventing an accidental rollback job from treating an expanded
schema as current.

## Canonical credential cutover

The release that introduces versioned `omnara_*_v1_…` credentials is an
intentional clean break from pre-canonical tokens. It does not migrate or revoke
old rows. Before deploying this release, plan to replace existing personal and
organization keys, install a newly issued token on each BYO machine, and
reprovision existing managed machines. Active old rows continue to count toward
the existing token quotas until you revoke them.

A mixed API fleet is unsafe during this one cutover: old APIs reject new
personal and organization keys, while new APIs reject every old credential.
Managed daemon credentials can be issued by the API during agent launch, by
workers through machine tools, and by maintenance reconciliation, so coordinate
all three processes. Either:

1. Upgrade or quiesce worker and maintenance issuers while every API remains on
   the old release. New daemon tokens work against the old API.
2. Pause credential issuance and provisioning, stop every old API replica, then
   start every new API replica together.

Or quiesce issuance/provisioning and replace API, worker, and maintenance as one
coordinated deployment. Do not leave an old managed-token issuer running after
any new API authenticator is serving. Daemon binaries themselves treat their
credential as opaque and do not need a lockstep upgrade.

If you roll the API back, newly issued personal and organization keys stop
working on the old binary; newly issued daemon tokens continue to work there.
Rolling a worker or maintenance process back while the new API remains live is
unsafe because it can resume issuing old daemon credentials.

## Exposing the deployment publicly

Email links, OAuth callbacks, the machine connect command, and cloud sandboxes all build URLs from `OMNARA_PUBLIC_URL`. These features will not function without this as a publicly-accessible URL.

<Warning>
  Set `OMNARA_PUBLIC_URL` on every backend service. Outside local development it is required.
</Warning>

### Cloudflare Tunnel

One easy option to expose Omnara publicly is via a [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/).

#### Persistent Tunnel (recommended)

For a stable origin, add a domain to Cloudflare and create a named tunnel:

```sh
brew install cloudflared   # or see Cloudflare's install docs
cloudflared tunnel login
cloudflared tunnel create omnara
cloudflared tunnel route dns omnara omnara.example.com # replace with your preferred domain
cloudflared tunnel run --url http://localhost:8000 omnara
```

Then, restart the stack pointed at the tunnel's URL:

```sh
OMNARA_PUBLIC_URL=https://omnara.example.com docker compose --profile app up -d
```

`cloudflared service install` will keep a named tunnel running across reboots. Any other reverse proxy or tunnel (Caddy, nginx, Tailscale Funnel, ngrok) works the same way, as long as it forwards the public `Host` header — the API rejects hosts it doesn't recognize.

#### Quick Tunnel

For a temporary tunnel without a separate domain, you can use:

```sh
cloudflared tunnel --url http://localhost:8000
```

This prints a random `https://<something>.trycloudflare.com` URL that changes every run. After starting the tunnel you can set `OMNARA_PUBLIC_URL` in the same way described above.
