All configuration is via environment variables. Use `.env.example` in the repo as a starting point.

<Note>
  **Required** refers to production. Setting
  `OMNARA_ALLOW_INSECURE_DEV_DEFAULTS=1` fills the fallbacks marked *dev* below
  (local Compose services, console email, an insecure secret-encryption key).
  Never set it in production.
</Note>

## Database and Redis

| Variable                   | Purpose                                                                                        | Default                           | Required |
| -------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------- | -------- |
| `OMNARA_DATABASE_URL`      | Postgres connection string used by `migrate` and the three long-running control-plane services | _dev:_ local Compose Postgres     | Yes      |
| `OMNARA_REDIS_URL`         | Redis or Valkey URL                                                                            | _dev:_ `redis://127.0.0.1:6379/0` | Yes      |
| `OMNARA_MIGRATIONS_DIR`    | Directory containing schema migrations; used only by `cmd/migrate`                             | `migrations`                      | No       |
| `OMNARA_MIGRATION_TIMEOUT` | Overall deadline for the one-shot migration process (Go duration)                              | `30m`                             | No       |

PostgreSQL 18 or newer is required. The API, worker, and maintenance services
default to a pool of 1–10 connections, a 30-minute idle timeout, a 30-minute
connection lifetime, and five minutes of lifetime jitter. Override these with
`pool_*` settings in `OMNARA_DATABASE_URL`, and budget connections across all
service replicas.

Direct PostgreSQL, RDS Proxy, and PgBouncer session pooling work with these
settings. PgBouncer transaction pooling requires `max_prepared_statements > 0`;
statement pooling is not supported.

The migrator defaults to a 30-second lock timeout and a 15-minute statement
timeout. Explicit values in `OMNARA_DATABASE_URL` take precedence.

## Channel gateway

The `channel-gateway` runs Slack receipt processing and bounded send, read, and interaction operations. Go verifies Slack's existing event callbacks and saves the event before acknowledging it; the gateway claims those durable receipts through the private API. Slack OAuth and signed actions also remain on the Go API. The gateway uses Hono, calls the API with a scoped connector token, and never connects to Postgres.

Generate a connector token with `make channel-connector-token`. Store it in your normal secret manager. API and worker need the same connector list; the gateway needs the matching token:

```sh
OMNARA_CHANNEL_CONNECTORS_JSON='[{"id":"primary","token":"<generated token>","operations_url":"http://channel-gateway:8080/internal/operations","capabilities":[{"connector_key":"chat_sdk","provider":"slack"}]}]'
OMNARA_CHANNEL_CONNECTOR_TOKEN='<generated token>'
```

Each capability is one exact connector-and-provider pair. The worker selects `operations_url` only from this deployment configuration; it must include the complete private `/internal/operations` path. Duplicate or ambiguous outbound routes are rejected. Omitting the URL allows inbound authentication but supplies no outgoing route. For processes running outside Compose, use service addresses they can reach.

Keep `/api/v1/channel-connector/*` and `/internal/operations` on the private service network. The bundled nginx gateway blocks both at the public edge; bearer authentication is still required. `OMNARA_INTERNAL_API_ORIGINS` belongs on the API and allows the exact private origin used by the gateway. Slack continues to use the event/action URLs returned by setup under `/api/integrations/slack/*`. The generic `/hooks/*` and polling/socket factory extension points do not enable additional providers: the built-in factory registry is empty, while Slack receipt and operation callbacks are wired separately.

Receipt consumers claim only available processing slots and bound each event's retries. Replaying a saved, verified receipt does not repeat live SDK signature verification or deduplication. Core atomically admits workflow launch, input, binding, and wakeup; a failed launch transaction leaves no partially admitted input. Terminal receipts remain available for the configured retention period. Receipt completion and retry authority stay in core.

Managed operations have one request deadline covering artifact transfer and provider attempts. The gateway may make an initial attempt plus up to three safe retries within it, respecting `Retry-After`. Permanent failures stop. An unknown non-idempotent outcome is terminal and must not be blindly retried. Core sends the HTTP mutation once and receives a completed, failed, or unknown result. There is no outgoing outbox or delivery polling loop. Customer-owned external connections use their separate finite request/completion lifecycle.

Outgoing artifacts stream into ephemeral files. The gateway validates the whole bounded multipart request before provider mutation and cleans up files on completion, cancellation, or connection loss. Configure enough local temporary storage for the per-process total-byte budget and size the per-request budget for your stored artifacts. These deployment budgets include actual bytes; they do not impose a new 10 MiB per-file product limit. The outgoing artifact count remains 20. Container termination can discard this temporary work; it is not a durable staging queue.

Provider credentials remain encrypted in Omnara's secret store. The gateway fetches authorized app and installation configuration from core; credentials are not stored in Redis. The built-in Slack receipt and operation callbacks run without a gateway Redis connection. Redis/Valkey is required only when provider factories are registered, for namespaced Chat SDK coordination and transient state. Those deployments must set `OMNARA_CHANNEL_REDIS_URL` and `OMNARA_CHANNEL_REDIS_TOPOLOGY` explicitly: `standalone` for one endpoint or `cluster` for Redis Cluster. Supplied Redis configuration is validated even when no factories are registered. Configuration generations and runtime leases fence stale work; they are independent of the unversioned `chat_sdk` capability key.

## Auth and SSO connectors

| Variable                             | Purpose                                   | Default | Required |
| ------------------------------------ | ----------------------------------------- | ------- | -------- |
| `OMNARA_AUTH_SIGNUP_ENABLED`         | First-party password signup               | `1`     | No       |
| `OMNARA_AUTH_PASSWORD_RESET_ENABLED` | Password reset flow                       | `1`     | No       |
| `OMNARA_AUTH_CONNECTORS_JSON`        | JSON array of social/SSO login connectors | —       | No       |

GitHub uses `kind:"github"` (endpoints default to github.com; GitHub-compatible providers must supply `issuer`, `authorization_url`, `token_url`, and `userinfo_url`). Google and generic SSO providers — Keycloak, Okta, Auth0, Azure, ZITADEL — use `kind:"oidc"` with issuer discovery. An example is shown below:

```sh
OMNARA_AUTH_CONNECTORS_JSON='[
  {"slug":"github","kind":"github","display_name":"GitHub","client_id":"{id}","client_secret":"{secret}"},
  {"slug":"google","kind":"oidc","display_name":"Google","issuer":"https://accounts.google.com","client_id":"{id}","client_secret":"{secret}","email_trust_policy":"verified_email"}
]'
```

## Secret encryption

Secret values are envelope-encrypted with keys from this ring.

| Variable                                 | Purpose                                                    | Default                         | Required |
| ---------------------------------------- | ---------------------------------------------------------- | ------------------------------- | -------- |
| `OMNARA_SECRET_ENCRYPTION_KEYS`          | JSON object of key ID to base64 32-byte key (the key ring) | _dev:_ insecure `dev-local` key | Yes      |
| `OMNARA_SECRET_ENCRYPTION_ACTIVE_KEY_ID` | Key ID used to wrap new writes; must exist in the ring     | _dev:_ `dev-local`              | Yes      |

Generate each key with `openssl rand -base64 32`. To rotate: add the new key to the ring, set it active, rewrap stored versions, then remove the old key once nothing references it.

| Provider   | CPU fields                                      | `provider_config`                                                                                                  | `default_machine_provider_options`                                                   |
| ---------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `unikraft` | Default and maximums required; minimum optional | Optional `api_base_url`, `allowed_images`, and `allowed_metros`                                                    | `image`, `metro`, and optional `startup_script` and `sleep_after_ms`                 |

| `modal`    | Default and maximums required; minimum optional | Optional `app` (defaults to `omnara`), `environment` (defaults to `main`), `allowed_images`, and `allowed_regions` | Public linux/amd64 `image` plus optional `region` and `startup_script`               |

Provider notes:

- Custom pool images must provide a writable `HOME` or `OMNARA_HOME`, plus a POSIX shell, standard Unix utilities, `curl`, and `sha256sum` or `shasum` for the Omnara launcher (`startup_script` additionally requires `base64`).
- Blaxel images must be sandbox images built or pushed through Blaxel (custom images must include `sandbox-api`), and unlimited persistence requires quota Tier 2 or higher — Tier 0 and Tier 1 cap sandbox lifetimes at 7 and 30 days.
- Daytona snapshots are allowed by name, must be active in the selected target, must allow sandboxes to reach `OMNARA_PUBLIC_URL`, and their API-resolved CPU and memory count against the pool caps.
- Modal credentials must be supplied as one JSON value containing `token_id` and `token_secret`. Omnara configures Modal sandboxes with a 24-hour timeout. Omit `region` for automatic placement. Create a non-`main` environment in Modal before configuring it. Use versioned image tags because Modal does not automatically repull a mutable external tag after caching it.
- For Unikraft and Blaxel, `sleep_after_ms` enables scale-to-zero after that many milliseconds of daemon inactivity; omit or `0` disables it, and enabled values must be at least `30000`.

### Operator-provisioned default model provider

An installation can give each new organization a model provider without storing
the upstream credential in configuration. Leave these variables unset to let
organization owners configure providers themselves.

| Variable                                 | Purpose                                                                                                        | Default | Required                         |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------- | -------------------------------- |
| `OMNARA_DEFAULT_MODEL_PROVIDER_TEMPLATE` | Path to the provider and model template on the API and maintenance. See `default-model-provider-example.yaml`. | —       | No                               |
| `OMNARA_HOSTED_API_URL`                  | Base URL of the operator credential service. Used by the API and maintenance.                                  | —       | With a default provider template |
| `OMNARA_HOSTED_API_TOKEN`                | Bearer token shared with the operator credential service; at least 32 bytes. Used by the API and maintenance.  | —       | With a default provider template |

Templates support the [token settings and timeouts](/organization/model-providers)
described for model providers.

To reconcile configured defaults into existing organizations, run these commands
with the same database and template environment as the API:

```sh
omnara-api reconcile-defaults plan
omnara-api reconcile-defaults apply
```

Review the plan before applying. Reconciliation updates installation-managed
defaults while preserving organization-owned providers and models, along with
explicit project grant overrides.

The credential service contract has these invariants:

- `POST /model-provider-credentials` receives the organization ID, creator user
  ID, and provider template. A successful response is `201` with
  `{"credential_value":"..."}`; `202` and `5xx` are retryable, while `409`
  represents a durable identity or provisioner conflict.
- The organization ID is the stable issuance identity. The same request may be
  repeated until Omnara commits the credential, provider, models, grants, and job
  completion together. The credential service must recover ambiguous issuance
  without returning an unusable credential.
- Organization creation never depends on credential issuance. The API attempts
  provisioning after commit, and maintenance retries failures.
- Apply migrations before deploying both binaries. The API and maintenance must
  use the same template, credential-service configuration, and secret-encryption
  key ring.
