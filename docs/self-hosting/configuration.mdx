<Note>
  **Required** refers to production. Setting
  `OMNARA_ALLOW_INSECURE_DEV_DEFAULTS=1` fills the fallbacks marked *dev* below
  (local Compose services, console email, an insecure secret-encryption key).
  Never set it in production.
</Note>

## Database and Redis

| Variable                   | Purpose                                                                                        | Default                           | Required |
| -------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------- | -------- |
| `OMNARA_DATABASE_URL`      | Postgres connection string used by `migrate` and the three long-running control-plane services | _dev:_ local Compose Postgres     | Yes      |
| `OMNARA_REDIS_URL`         | Redis or Valkey URL                                                                            | _dev:_ `redis://127.0.0.1:6379/0` | Yes      |
| `OMNARA_MIGRATIONS_DIR`    | Directory containing schema migrations; used only by `cmd/migrate`                             | `migrations`                      | No       |
| `OMNARA_MIGRATION_TIMEOUT` | Overall deadline for the one-shot migration process (Go duration)                              | `30m`                             | No       |

PostgreSQL 18 or newer is required. The API, worker, and maintenance services
default to a pool of 1–10 connections, a 30-minute idle timeout, a 30-minute
connection lifetime, and five minutes of lifetime jitter. Override these with
`pool_*` settings in `OMNARA_DATABASE_URL`, and budget connections across all
service replicas.

Direct PostgreSQL, RDS Proxy, and PgBouncer session pooling work with these
settings. PgBouncer transaction pooling requires `max_prepared_statements > 0`;
statement pooling is not supported.

The migrator defaults to a 30-second lock timeout and a 15-minute statement
timeout. Explicit values in `OMNARA_DATABASE_URL` take precedence.

## Channel gateway

The optional `channel-gateway` receives provider callbacks at `/hooks/*`, claims durable outbound deliveries through the API, and supervises provider polling or socket runtimes. It uses Redis directly for app-scoped Chat SDK state, but never connects to Postgres. Its state adapter uses only single-key commands, so it works with either standalone Redis/Valkey or Redis Cluster. Set `OMNARA_CHANNEL_REDIS_TOPOLOGY` explicitly: use `standalone` for one Redis endpoint and `cluster` for Redis Cluster or a cluster-compatible managed service.

Thread subscriptions are spread across fixed per-app shards instead of one global Redis set. Configuration refreshes preserve them. After a later request tells the gateway that an app was deleted, cleanup waits for that app's in-flight work to finish and then unlinks its shards. A known-app marker prevents arbitrary unknown webhook IDs from triggering a shard sweep. That marker is refreshed after successful app loads and cleanup attempts, then expires after 30 days so deleted-app tombstones do not grow forever. This window lets stale gateway instances recreate a subscription without making it permanent: a later deletion observation will sweep the shards again. If no gateway sees a deleted app before its marker expires, its inert subscription keys may remain until an operational Redis cleanup; core authorization still makes them unusable.

Generate a connector token with `make channel-connector-token`. Store it in your normal secret manager, then inject the same token into one gateway deployment and the API allowlist. Each allowlisted capability is one exact connector-and-provider pair; separate lists are deliberately not used because they could accidentally authorize combinations the gateway does not implement:

```sh
OMNARA_CHANNEL_CONNECTORS_JSON='[{"id":"primary","token":"<generated token>","capabilities":[{"connector_key":"chat_sdk_v1","provider":"discord"}]}]'
OMNARA_CHANNEL_CONNECTOR_TOKEN='<generated token>'
```

The API reads `OMNARA_CHANNEL_CONNECTORS_JSON` and `OMNARA_INTERNAL_API_ORIGINS`; maintenance reads `OMNARA_INTEGRATION_DELIVERY_RETENTION`; the gateway reads the remaining variables below. Keep the connector API on the private service network and expose only `/hooks/*` to channel providers. The bundled nginx gateway blocks public access to `/api/v1/channel-connector/*`; the bearer token is still required as the authorization boundary.

Customer provider credentials remain encrypted in Omnara's Postgres-backed secret store. The gateway asks the API for one exact app or installation at a time, keeps that result only in a bounded in-memory cache, and never writes decrypted credentials to Redis. Non-subscription Chat SDK cache and list state expires after at most 30 days. Webhook configuration can remain cached for at most `OMNARA_CHANNEL_APP_REFRESH_MS` before the next use refreshes it; claimed deliveries and runtimes also carry revisions that force an exact refresh after rotation. A gateway build must contain the named provider adapter. The provider-neutral foundation contains no adapters and therefore cannot enable a provider on its own.

Inbound callbacks use bounded retries with idempotent replay rather than a durable inbox. If an agent is launched from a profile but its channel input cannot be committed, the API returns `503`; replay resolves the same agent and reuses the event's media, binding, and input idempotency keys. Some providers acknowledge a callback before background Chat SDK work finishes, so exhausted retries can still leave a rare unused agent or drop that callback. The gateway logs those terminal background failures with the app and provider event IDs. Add a durable inbound receipt queue later if the product requires a stronger guarantee.

Webhook adapters may submit inbound work only while handling that exact request. Polling and socket sources must start inside a claimed runtime unit and stop when its lease signal is canceled; adapter initialization may register handlers but cannot act as an unfenced inbound source. This keeps a stale gateway from continuing to write after another instance takes over the runtime unit.

Outbound delivery is intentionally robust rather than exactly once. Definite failures before a provider send are retried with bounded backoff, up to eight attempts. Once a provider request has started, an ambiguous result becomes terminal `unknown` instead of risking a duplicate message. On shutdown the gateway stops claiming work, lets already-started sends finish within their existing deadlines, and reserves part of each lease for recording the result. If that result still cannot be recorded, maintenance marks the expired claim `unknown`. Every provider delivery handler must pass the supplied abort signal or a shorter finite deadline into the actual provider network request; the common Chat SDK wrapper does not use its generic `post()` fallback because that API cannot guarantee cancellation.

A custom or bring-your-own gateway can use the same connector API without Chat SDK. It must follow the same delivery rule: bound its provider attempts, return `retry_wait` only before another safe attempt, and return terminal `unknown` whenever a started provider request has an ambiguous result. Core reports the claim count and fails a delivery after 64 total claims as a final protection against a broken connector; adapters should use a much lower bound for actual provider I/O.

The gateway pins Chat SDK `4.39.0`. Its serialized concurrency strategies now renew distributed handler locks while work is running, with a bounded ten-minute renewal lifetime by default. The gateway keeps `concurrent` as its provider-neutral default; each adapter can select a serialized strategy and a different `maxLockLifetimeMs` when its delivery semantics require one. An exact-version exception admits this reviewed correctness release before the repository's ten-day dependency quarantine expires; remove that exception after `2026-09-07T10:46:04Z`. No other Chat SDK version bypasses the quarantine.

The first real provider-adapter release is also the contract step for installation identity. Deploy this foundation to every API instance first. That later release must add a migration that drops `integration_installs_provider_tenant_account_idx` before it enables multiple apps for the same provider account. This foundation already writes and reads the replacement app-scoped identity; the old index remains temporarily because pre-foundation API binaries still name it in `INSERT ... ON CONFLICT` and would fail during a rolling deployment if it disappeared here.

Each provider adapter must also cap attachment bytes and download time while reading the provider response. Declared attachment sizes are only a preflight hint: the common gateway checks the final bytes too, but it cannot undo memory already allocated by an adapter's `fetchData`. Provider packages must therefore enforce the same limit at their HTTP streaming boundary and include an oversized or dishonest-content-length regression before they are registered.

```sh

  {"slug":"github","kind":"github","display_name":"GitHub","client_id":"{id}","client_secret":"{secret}"},
  {"slug":"google","kind":"oidc","display_name":"Google","issuer":"https://accounts.google.com","client_id":"{id}","client_secret":"{secret}","email_trust_policy":"verified_email"}
]'
```

Secret values are envelope-encrypted with keys from this ring.

| Variable                                 | Purpose                                                    | Default                         | Required |

Provider notes:

- Custom pool images must provide a writable `HOME` or `OMNARA_HOME`, plus a POSIX shell, standard Unix utilities, `curl`, and `sha256sum` or `shasum` for the Omnara launcher (`startup_script` additionally requires `base64`).

- For Unikraft and Blaxel, `sleep_after_ms` enables scale-to-zero after that many milliseconds of daemon inactivity; omit or `0` disables it, and enabled values must be at least `30000`.

### Operator-provisioned default model provider

An installation can give each new organization a model provider without storing
the upstream credential in configuration. Leave these variables unset to let
organization owners configure providers themselves.

| Variable                                 | Purpose                                                                                                        | Default | Required                         |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------- | -------------------------------- |
| `OMNARA_DEFAULT_MODEL_PROVIDER_TEMPLATE` | Path to the provider and model template on the API and maintenance. See `default-model-provider-example.yaml`. | —       | No                               |
| `OMNARA_HOSTED_API_URL`                  | Base URL of the operator credential service. Used by the API and maintenance.                                  | —       | With a default provider template |
| `OMNARA_HOSTED_API_TOKEN`                | Bearer token shared with the operator credential service; at least 32 bytes. Used by the API and maintenance.  | —       | With a default provider template |

The credential service contract has these invariants:

- `POST /model-provider-credentials` receives the organization ID, creator user
  ID, and provider template. A successful response is `201` with
  `{"credential_value":"..."}`; `202` and `5xx` are retryable, while `409`
  represents a durable identity or provisioner conflict.
- The organization ID is the stable issuance identity. The same request may be
  repeated until Omnara commits the credential, provider, models, grants, and job
  completion together. The credential service must recover ambiguous issuance
  without returning an unusable credential.
- Organization creation never depends on credential issuance. The API attempts
  provisioning after commit, and maintenance retries failures.
- Apply migrations before deploying both binaries. The API and maintenance must
  use the same template, credential-service configuration, and secret-encryption
  key ring.
