<Note>
  **Required** refers to production. Setting
  `OMNARA_ALLOW_INSECURE_DEV_DEFAULTS=1` fills the fallbacks marked *dev* below
  (local Compose services, console email, an insecure secret-encryption key).
  Never set it in production.
</Note>

## Database and Redis

| Variable                   | Purpose                                                                                        | Default                           | Required |
| -------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------- | -------- |
| `OMNARA_DATABASE_URL`      | Postgres connection string used by `migrate` and the three long-running control-plane services | _dev:_ local Compose Postgres     | Yes      |
| `OMNARA_REDIS_URL`         | Redis or Valkey URL                                                                            | _dev:_ `redis://127.0.0.1:6379/0` | Yes      |
| `OMNARA_MIGRATIONS_DIR`    | Directory containing schema migrations; used only by `cmd/migrate`                             | `migrations`                      | No       |
| `OMNARA_MIGRATION_TIMEOUT` | Overall deadline for the one-shot migration process (Go duration)                              | `30m`                             | No       |

PostgreSQL 18 or newer is required. The API, worker, and maintenance services
default to a pool of 1–10 connections, a 30-minute idle timeout, a 30-minute
connection lifetime, and five minutes of lifetime jitter. Override these with
`pool_*` settings in `OMNARA_DATABASE_URL`, and budget connections across all
service replicas.

Direct PostgreSQL, RDS Proxy, and PgBouncer session pooling work with these
settings. PgBouncer transaction pooling requires `max_prepared_statements > 0`;
statement pooling is not supported.

The migrator defaults to a 30-second lock timeout and a 15-minute statement
timeout. Explicit values in `OMNARA_DATABASE_URL` take precedence.

## Channel gateway

The `channel-gateway` runs the built-in Slack, Discord, and GitHub transports and conversation behavior. It calls Omnara's private API with a scoped connector token; it never connects to Postgres. Core owns project authorization, encrypted credentials, durable incoming events, and atomic agent admission. The gateway owns provider requests, webhook handling, and Discord Gateway connections.

Generate a connector token with `make channel-connector-token`. Store it in your normal secret manager. API and worker need the same connector list; the gateway needs the matching token:

```sh
OMNARA_CHANNEL_CONNECTORS_JSON='[{"id":"primary","token":"<generated token>","operations_url":"http://channel-gateway:8080/internal/operations","capabilities":[{"connector_key":"omnara","provider":"slack"},{"connector_key":"omnara","provider":"discord"},{"connector_key":"omnara","provider":"github"}]}]'
OMNARA_CHANNEL_CONNECTOR_TOKEN='<generated token>'
```

Each capability is one exact connector-and-provider pair. The worker selects `operations_url` only from this deployment configuration; it must include the complete private `/internal/operations` path. Duplicate or ambiguous outbound routes are rejected. Omitting the URL allows inbound authentication but supplies no outgoing route. For processes running outside Compose, use service addresses they can reach.

Keep `/api/v1/channel-connector/*` and `/internal/operations` on the private service network. The bundled nginx gateway blocks both at the public edge; bearer authentication is still required. `OMNARA_INTERNAL_API_ORIGINS` belongs on the API and allows the exact private origin used by the gateway. Slack continues to use the event/action URLs returned by setup under `/api/integrations/slack/*`, routed to the API. GitHub's public webhook URL is `/hooks/<integration-app-id>/github/events`, routed to the gateway. Discord uses outbound Gateway sockets and needs no public message webhook. OAuth callbacks for all three use `/api/integrations/oauth/callback` on the API.

GitHub does not automatically retry failed webhook deliveries. If intake is
unavailable before an event is saved, recover through the app's recent-delivery
redelivery controls. Once saved, Omnara retries processing from its inbox.
See [GitHub redelivery](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks).

Receipt consumers claim only available processing slots and bound each event's retries. Replaying a saved, verified receipt does not repeat live SDK signature verification or deduplication. Core atomically admits workflow launch, input, binding, and wakeup; a failed launch transaction leaves no partially admitted input. Terminal receipts remain available for the configured retention period. Receipt completion and retry authority stay in core.

Provider retry delays postpone the next receipt claim without holding a gateway
worker. Core uses the longer of its own backoff and the connector's supplied delay
(up to one day); the existing message attempt budget still applies.

GitHub installation and repository-access updates use a separate app-owned
inbox because one provider installation can affect connections in several
projects. These updates are also saved before acknowledgment. Processing records
the last updated connection and resumes after a restart, using a fixed scan
boundary so new connections cannot extend that delivery indefinitely. Transient
failures retry with bounded backoff and provider rate-limit delays; successful
progress does not consume a total retry allowance. Invalid saved work and retired
owners stop processing. Each connection update still checks its project authority.
One control worker per gateway shares the global memory budget and may reserve
at most half of it, leaving capacity for incoming messages.
Maintenance exposes `omnara_integration_control_oldest_unapplied_timestamp_seconds`
and `omnara_integration_control_last_observation_timestamp_seconds` on its metrics
endpoint. A growing age for a nonzero oldest timestamp identifies a backlog of
connection updates; the observation timestamp shows whether that measurement is
still being refreshed. An observed empty inbox has an oldest timestamp of zero.
GitHub access updates recheck the installation's connected repositories, so large
installations or bursts of updates can encounter provider rate limits and take
longer to finish. Account for those delays when choosing backlog alert thresholds.

Managed operations have one request deadline covering artifact transfer and provider attempts. The gateway may make an initial attempt plus up to three safe retries within it, respecting `Retry-After`. Permanent failures stop. An unknown non-idempotent outcome is terminal and must not be blindly retried. Core sends the HTTP mutation once and receives a completed, failed, or unknown result. There is no outgoing outbox or delivery polling loop. Customer-owned external connections use their separate finite request/completion lifecycle.

Outgoing artifacts stream into ephemeral files. The gateway validates the whole bounded multipart request before provider mutation and cleans up files on completion, cancellation, or connection loss. Configure enough local temporary storage for the per-process total-byte budget and size the per-request budget for your stored artifacts. These deployment budgets include actual bytes; they do not impose a new 10 MiB per-file product limit. The outgoing artifact count remains 20. Container termination can discard this temporary work; it is not a durable staging queue.

Slack setup, OAuth, and event intake that requires gateway processing return HTTP 503 when the API has no configured exact `omnara`/`slack` capability. This checks deployment configuration, not gateway health. With that capability configured, core still durably accepts verified events during a temporary gateway outage; processing resumes from the inbox when the gateway recovers.

Provider credentials remain encrypted in Omnara's secret store. The gateway fetches authorized configuration from core: Slack's installation bot token, Discord's app bot token, or GitHub's app private key and webhook secret. OAuth client secrets stay in core. Gateway Redis does not contain these runtime credentials. During GitHub setup only, core keeps the user's authorization token in an encrypted, single-use Redis session for at most ten minutes; it is never a runtime bot credential.

The built-in gateway requires Redis/Valkey for provider coordination and transient state. Set `OMNARA_CHANNEL_REDIS_URL` and `OMNARA_CHANNEL_REDIS_TOPOLOGY` explicitly: `standalone` for one endpoint or `cluster` for Redis Cluster. Compose supplies the local Redis defaults. Configuration generations and runtime leases fence stale work; they are independent of the unversioned `omnara` capability key. Incoming communication is saved in core's Postgres inbox before webhook acknowledgment or advancing Discord's recoverable sequence.

Discord gateway shards belong to the app and are shared by its guild connections.
The first verified setup initializes the shard set; reconnect preserves its count
and checkpoints even if Discord now recommends more shards. That recommendation
does not automatically reshard the app or reject reconnection. Changing the count
requires deliberate maintenance through the existing runtime-unit storage
operations: keep the complete set's shard counts and specification revisions
consistent and stop obsolete units. Gateway claim capacity controls placement,
not the configured shard count.

### Apps and project connections

Organization managers register a provider app under **Apps** and select its
credential secret. An app can serve the organization or be restricted to one
project. Project managers then connect a Slack workspace, Discord server, or
GitHub repository under **Integrations**. The installation, registered channels,
and agent bindings belong to that project. One physical app's external account
cannot be connected to multiple projects at once.

For Discord, enable the app's **Requires OAuth2 Code Grant** setting and
**Message Content Intent** before connecting. Setup verifies the bot/app identity
and server access before creating the connection. For GitHub, register the OAuth
callback above, enable expiring user authorization tokens, and disable
**Request user authorization (OAuth) during installation**. Grant **Pull requests:
read and write**, **Issues: read**, and **Metadata: read**. Subscribe to pull request,
issue comment, pull request review, and pull request review comment events;
installation and repository-access events keep Omnara's local availability state
current. Set the app's webhook secret and gateway URL. Omnara does not request
Contents access or provide a machine checkout through this connection.

GitHub setup authorizes the user before showing their installation/repository
picker. If needed, install the verified app in another tab and refresh the picker.
The final selection requires fresh repository-administrator access. A temporary
organization installation-approval delay does not grant access prematurely.

Choose an optional inbound agent profile for a connection. Changing or clearing
it affects future launches; existing conversations keep their agents and grants.
Without a launch profile, registered channels can still be used for explicit
agent bindings and scheduled messages. A profile schedule's `channel_bindings`
grants access to every agent it launches. Reply-channel grants can allow that
agent to continue in a thread created by its message, without receiving every
message in the parent channel. Grants authorize access; integration behavior
independently decides when to deliver incoming events.

Disabling or removing an Omnara connection stops its local work and access. It
does not delete GitHub comments, dismiss or publish reviews, or otherwise mutate
GitHub's state. Permission and question prompts always remain available in the
Omnara dashboard; Discord and GitHub currently advertise no interactive prompts.

## Secret encryption

Secret values are envelope-encrypted with keys from this ring.

| Variable                                 | Purpose                                                    | Default                         | Required |
| ---------------------------------------- | ---------------------------------------------------------- | ------------------------------- | -------- |
| `OMNARA_SECRET_ENCRYPTION_KEYS`          | JSON object of key ID to base64 32-byte key (the key ring) | _dev:_ insecure `dev-local` key | Yes      |

Provider notes:

- Custom pool images must provide a writable `HOME` or `OMNARA_HOME`, plus a POSIX shell, standard Unix utilities, `curl`, and `sha256sum` or `shasum` for the Omnara launcher (`startup_script` additionally requires `base64`).
- Blaxel images must be sandbox images built or pushed through Blaxel (custom images must include `sandbox-api`), and unlimited persistence requires quota Tier 2 or higher — Tier 0 and Tier 1 cap sandbox lifetimes at 7 and 30 days.
- Daytona snapshots are allowed by name, must be active in the selected target, must allow sandboxes to reach `OMNARA_PUBLIC_URL`, and their API-resolved CPU and memory count against the pool caps.
- Modal credentials must be supplied as one JSON value containing `token_id` and `token_secret`. Omnara configures Modal sandboxes with a 24-hour timeout. Omit `region` for automatic placement. Create a non-`main` environment in Modal before configuring it. Use versioned image tags because Modal does not automatically repull a mutable external tag after caching it.
- For Unikraft and Blaxel, `sleep_after_ms` enables scale-to-zero after that many milliseconds of daemon inactivity; omit or `0` disables it, and enabled values must be at least `30000`.

### Operator-provisioned default model provider

An installation can give each new organization a model provider without storing

| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------- | -------------------------------- |

| `OMNARA_HOSTED_API_URL`                  | Base URL of the operator credential service. Used by the API and maintenance.                                  | —       | With a default provider template |
| `OMNARA_HOSTED_API_TOKEN`                | Bearer token shared with the operator credential service; at least 32 bytes. Used by the API and maintenance.  | —       | With a default provider template |

Templates support the [token settings and timeouts](/organization/model-providers)
described for model providers.

To reconcile configured defaults into existing organizations, run these commands
with the same database and template environment as the API:

```sh
omnara-api reconcile-defaults plan
omnara-api reconcile-defaults apply
```

Review the plan before applying. Reconciliation updates installation-managed
defaults while preserving organization-owned providers and models, along with
explicit project grant overrides.

The credential service contract has these invariants:

- `POST /model-provider-credentials` receives the organization ID, creator user
  ID, and provider template. A successful response is `201` with
  `{"credential_value":"..."}`; `202` and `5xx` are retryable, while `409`
  represents a durable identity or provisioner conflict.
- The organization ID is the stable issuance identity. The same request may be
  repeated until Omnara commits the credential, provider, models, grants, and job
  completion together. The credential service must recover ambiguous issuance
  without returning an unusable credential.
- Organization creation never depends on credential issuance. The API attempts
  provisioning after commit, and maintenance retries failures.
- Apply migrations before deploying both binaries. The API and maintenance must
  use the same template, credential-service configuration, and secret-encryption
  key ring.

### Host daemon configuration

| Variable                  | Purpose                                                                                                                                                        | Default                                                             |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `OMNARA_HOME`             | Binary, configuration, logs, locks, and runtime state                                                                                                          | `$HOME/.omnarad`                                                    |
| `OMNARA_API_URL`          | API root URL, including the `/api/v1` mount for self-hosted deployments; HTTP is accepted only for loopback or `host.docker.internal` during local development | Existing `daemon.json` value, otherwise `https://api.omnara.com/v1` |
| `OMNARA_MACHINE_TOKEN`    | Machine token; prompted for by the installer when omitted                                                                                                      | Existing `daemon.json` value                                        |
| `OMNARA_NO_UPDATE`        | Set to `1` or `0` to temporarily disable or enable managed updates                                                                                             | Existing `daemon.json` value, otherwise `0`                         |
| `OMNARA_RUNNER_PATH`      | Temporary `PATH` override for agent commands                                                                                                                   | Existing `daemon.json` value, otherwise the installation `PATH`     |
| `OMNARA_DAEMON_SEED_PATH` | Existing `omnarad` binary used only to seed a fresh installer-owned home                                                                                       | —                                                                   |

| Variable      | Purpose                                                                                         | Default | Required |
