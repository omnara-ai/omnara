An app connects your project to a service such as Slack, Discord or GitHub. It
owns the provider setup, credentials and optional launch behavior. Create it once,
then select its tools and handlers in agent configs and attach conversations to
agents. Customers running their own service
can use the ordinary [inputs, custom tools and interaction APIs](/integrations/custom-integrations).

## Create an app

Open **Apps** under your project and select an app type. If you already have apps,
choose **Add app** first. Enter its unique name and connection details together
on the setup page, then choose launch profiles after connecting. If connection
fails, retrying reuses the saved app and credentials. You can also reopen the
saved app from **Apps** to finish later. The name follows the
same rules as an MCP server name: a letter followed by letters, digits or hyphens,
up to 32 characters. Names and app types cannot be changed after creation.

The app type identifies its behavior: `slack_thread`, `discord_thread` or
`github_pr`. Create and update requests use `app_type`, for example:

```json
{"name":"engineering","app_type":"slack_thread","settings":{}}
```

`GET /orgs/{orgID}/projects/{projectID}/app-definitions` lists each registered
`app_type` and its `capabilities`. Saved apps also expose `app_type`; neither
record includes a provider classification. Code contributors register a precise
behavior type without an `omnara.` prefix, following the
[app implementation guide](https://github.com/omnara-ai/omnara/blob/main/internal/integration/CONTRIBUTING.md).

A saved app starts disconnected. Connecting verifies its provider identity and
saves a reference to encrypted credentials. Add profiles and a launcher when
provider events should start agents. Schedules and interaction handlers can be used
without an event launcher. The shipped thread and PR tools require the conversation
assigned by their app when launching an agent.
There is no separate connection object to create or share. Two apps configured
with the same bot remain independent setups, with separate credential updates
and lifecycle. Avoid overlapping launchers for the same conversation: duplicate
menus, agents or replies are possible.

The detail page shows setup state, launch settings, available capabilities and a
paginated **Conversations** list with each destination agent.
Changing offered profiles affects future launches. Disconnecting stops provider
access and pauses subscription delivery. Its conversations remain visible and can
still be removed while disconnected. Deleting an app removes its schedules and
subscriptions and releases its credential reference. Neither action removes agents, their history, or messages already
posted in the provider. Agents remain usable through the dashboard and API.

## Connect GitHub

Choose whether the GitHub App belongs to your personal account or an organization,
then select **Continue to GitHub**. GitHub handles registration and installation;
Omnara fills in the required webhook, events and permissions. The new GitHub App
is private by default. To install it outside its owning account, change its
visibility in GitHub's App settings.

After registration, install the App on GitHub and select which repositories it
can access. Return to Omnara, select the verified installation and connect it.
Credentials are saved before installation, so you can finish later if an
organization must approve the installation. **Use an existing App** remains
available for an App you have already registered or for manual reconnection.

Choose the agent profile and whether a mention or opening a PR starts an agent.
New launchers apply to the repositories granted to that installation. Manage
repository access in GitHub; Omnara does not maintain another repository allowlist
in this setup flow. Existing saved repository restrictions are preserved when
editing a launcher. Repository checkout and machine credentials remain separate
from the App's PR comment permissions.

## Select capabilities independently

An app can supply tools, named subscription types and one interaction handler.
A tool lets the model act; an app-owned subscription forwards incoming events to
an agent; a handler presents questions and approvals outside the dashboard.
Configs select tools and handlers. Launch requests or the subscriptions API attach
conversations independently of config.
The launcher is separate: it decides whether and how to start agents.

For example, a profile selected by a GitHub app named `reviews` can also use the
interaction handler of a Slack app named `engineering`. Its config can include:

```yaml
instruction: |
  Review the pull request that launched you. Select engineering as your interaction
  handler with channel_id C123 before requesting approval.
model:
  provider_config: my-provider
  name: my-model
tools:
  ask_question: {}
  app__reviews__read: {}
interaction_handlers:
  engineering: {}
```

Tools use `app__<app-name>__<operation>`, with one entry per app and operation.
Tool entries select enabled state, deferred loading and permissions. Handler entries
are empty objects. Interaction handlers take destination arguments; tools use the
conversation assigned at launch.
The catalog exposes the static argument schema in
`capabilities.tools[operation].input_schema` and
`capabilities.interaction_handler.input_schema`.

A provider or scheduled launch records one immutable conversation for that app
and agent. Slack and Discord tools use that conversation; GitHub tools use that pull
request. Calls contain only the action and pagination arguments, such as
`{"text":"Update"}` or `{"section":"files","page":2}`. Tools fail before contacting
the provider if the agent has no assigned conversation. Adding a subscription or
selecting an interaction handler does not establish or change sending context.

The app's credential permissions remain the provider access boundary; Omnara also
checks project ownership, current app status and ordinary
[tool permission](/tools/permissions). The
[OpenAPI contract](/api-reference/openapi.yaml) defines the catalog and launch API.

Names are resolved to immutable app IDs, not app types, when the config is
compiled. Deleting an app and reusing its name does not redirect old agents. Re-save profiles that should
use the replacement app before their launchers run; old pinned references are not
automatically rebound. Credentials are loaded
live, so rotation does not require rewriting configs. A pending tool call cannot
silently acquire a different app, sending context or permission after a config change.

## Subscribe a conversation

A subscription connects one app, one agent, a named type and one concrete provider
conversation. Multiple apps or conversations can forward to the same agent.
Subscriptions belong to the app: saving, activating or changing an agent config
never adds or removes them. Source YAML has no `listeners` block.

The app and app-definition catalog expose
`capabilities.subscriptions[type].conversation_schema` and `.events`. The type is
local to the app, such as `thread_messages` or `pull_request`; do not prefix it
with the app name. The conversation is one flat provider address, not a config
or a list. Omit `events` to use the definition's defaults.

For an existing agent, send this body to
`POST /orgs/{orgID}/projects/{projectID}/apps/{appID}/subscriptions`:

```json
{
  "agent_id": "YOUR_AGENT_ID",
  "type": "thread_messages",
  "conversation": {"channel_id": "C123", "thread_ts": "111.222333"}
}
```

For a new agent, include `subscriptions` in its
[launch request](/agents/overview#attach-apps-and-an-initial-input-atomically).
Each attachment has `app_id`, `type`, `conversation` and optional `events`.
The subscriptions and initial input are committed with the agent before its first
step. Attaching only subscriptions does not derive a new config.

Use `GET` on the same app subscriptions path with `limit` and optional `cursor`
to list conversations. The response contains `data` and `next_cursor`; each row
includes its `asub_…` ID, app, project, agent ID/name, type, concrete conversation,
resolved events and creation time. Listing requires project read permission;
creation and deletion require project management permission.

### Stop forwarding

Open the app's **Conversations** section and choose **Stop forwarding**, or call
`DELETE /orgs/{orgID}/projects/{projectID}/apps/{appID}/subscriptions/{subscriptionID}`.
This stops incoming forwarding for that subscription. The agent, sending tools,
interaction handlers and history remain. A stopped selected thread does not
launch a replacement agent on the next mention. Explicitly attach the conversation
again through the API to resume forwarding. Independent existing-agent launcher
slots and already accepted chooser handoffs are not canceled by this deletion.

Repeating an active attachment returns the same subscription. A different event
selection for that attachment is a conflict: delete it and attach again to change
the filter. A fresh attachment after deletion receives a new ID, so retrying an old
DELETE cannot remove the new attachment. App disconnection preserves subscriptions;
app deletion or agent archival removes them.

Sending and receiving are independent. Posting a message does not create or
restore subscriptions. To start a fresh scheduled agent in a new thread, configure
an app schedule; the launch assigns its sending conversation and reply subscription.

## Launch from provider events

[Slack](/integrations/slack) and [Discord](/integrations/discord) create thread
agents from mentions. With one offered profile, the agent starts immediately.
With several profiles, the bot presents a selection menu and starts only the
chosen profile. [GitHub](/integrations/github) can start work from a PR mention
or PR creation; its launcher runs each configured slot.

A profile launch derives a config with the app's tools and supported interaction
handler, and separately attaches a subscription for that conversation. The profile
stays unchanged. Existing explicit entries win as complete entries, including
disabled tools and permissions. The launcher adds missing entries only; the
capability additions are the same for every conversation using that profile and
app. The destination belongs to the app-agent context, not the derived config.
An existing-agent launcher slot forwards input without adding capabilities or
sending context.

The create-agent API accepts `tools` and `interaction_handlers` when deriving a
config from a pinned config or profile, plus independent `subscriptions`
attachments. Config authoring and app management require project management permission. App credential setup requires a
user session or personal access token; organization API keys can perform ordinary
runtime work. App capabilities and runtime subscriptions are not inherited by subagents.

Ordinary model output stays in Omnara. Posting externally requires an app tool.

## Start a new thread on a schedule

Open a Slack or Discord app from the project's **Apps** page and choose **Add
schedule**. Select one profile, the parent channel, the schedule and timezone,
an opening-message template, and the task to give the agent. Mention launches
and schedules are independent; the same app can use either or both.

For each occurrence, the app posts the opening message and then launches a fresh
agent in its thread. The agent receives thread tools, a reply subscription, and an
interaction handler before its first step. The profile's existing explicit
entries still win. Ask the agent to post its report using the app tool; normal
model output remains in Omnara. Replies in Monday's thread continue Monday's
agent, while Tuesday's run creates a new thread and agent.

Both templates support the existing cron variables. `{{.trigger.local_date}}`
is the occurrence's scheduled date in its timezone, formatted `YYYY-MM-DD`.
The opening message is limited to 2,000 characters. Slack schedules require a
channel the bot has already joined, not a DM; Discord schedules require a server
text or announcement channel.

Schedules use the ordinary cron API with an app target. The app catalog publishes
the schema for `settings`; cron does not interpret those fields:

```json
{
  "name": "Daily engineering update",
  "cron": "0 9 * * 1-5",
  "timezone": "America/Los_Angeles",
  "target": {
    "type": "app",
    "app_id": "YOUR_APP_ID",
    "settings": {
      "agent_profile_id": "YOUR_PROFILE_ID",
      "channel_id": "C123",
      "opening_message_template": "Engineering update — {{.trigger.local_date}}",
      "message_template": "Review today's activity and post a summary in this thread."
    }
  }
}
```

The schedule shows whether the latest run is queued, processing, completed, failed,
or discarded, alongside its last update time. **Completed** means the app handled
that scheduled occurrence. For the thread apps, that means the agent started;
it does not mean the agent finished its task or posted a report. Run details expire with
inbox retention. A disconnected app skips an occurrence with a visible failure;
later scheduled occurrences can run after reconnection. Disabling or deleting a
schedule stops future firings; it does not cancel work already accepted by the
app. The target app is fixed. Settings, including the thread app's profile, can
change for future occurrences; an accepted occurrence retains its settings.
Deleting the app deletes its schedules. Deleting a profile does not delete app
schedules that reference it: those runs fail visibly until the settings are corrected.

The thread app resolves the profile's current configuration while building its
launch plan. Once saved, that plan keeps the same configuration across retries.
An opening message can remain if the later agent launch fails. Once the thread's
launch plan is saved, retries reuse that thread. A reported uncertain send or a
failure saving the plan after publication fails the run. If a crash, lost lease,
or database outage prevents saving either the plan or the failure, recovery may
post another opening and leave the earlier heading unused. Explicit operator retry
of a failed run without a saved plan can also post a replacement. Each occurrence
still admits at most one agent. Questions and approvals remain available in the
dashboard if provider delivery fails.

## Route questions and approvals

Tool-capable configs include `list_interaction_handlers` and
`set_interaction_handler` by default, unless explicitly disabled. The list is
paginated and returns each handler's description and static argument schema,
plus the current selection independently of the page. The model selects a handler
and destination arguments, or uses `{"handler": null, "args": {}}` for dashboard only.

Selecting a handler requires complete destination arguments, independently of the
app's sending context. For example:

```json
{"handler":"engineering","args":{"channel_id":"C123","thread_ts":"111.222333"}}
```

A handler may use another conversation accessible to the app; it is not restricted
to the sending context. Anyone able to respond in that provider conversation can
answer its questions and approvals; they do not need an Omnara account. Choose a
destination whose audience you trust to make those decisions.

A newly accepted provider input selects a unique matching handler with the complete
origin address for future interactions, including the initial launch input. No
matching handler means dashboard only; an input without a provider origin preserves
the selection. Each interaction captures its destination
when created, so changing the selection does not move an existing prompt.

The dashboard remains available if provider presentation fails. Removing a handler,
disconnecting its app, or replacing the pinned app invalidates old external
callbacks. Captured interaction responses contain complete destination `args`.
See [interactions](/events/interactions) for answering through the API.

For an existing Slack deployment, use the coordinated
[maintenance cutover](/self-hosting/composable-apps-cutover). Self-hosted operators
can inspect, retry or discard failed inbound receipts with the
[recovery commands](/self-hosting/composable-apps-cutover#recover-failed-app-events).
