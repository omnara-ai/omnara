An app connects your project to a service such as Slack, Discord or GitHub. It
owns the provider setup, credentials and optional launch behavior. Create it once,
then use its capabilities in agent configs. Customers running their own service
can use the ordinary [inputs, custom tools and interaction APIs](/integrations/custom-integrations).

## Create an app

Open **Apps** under your project, choose **Add app**, and select an app type. Give
it a unique name, save it, and complete the provider setup. The name follows the
same rules as an MCP server name: a letter followed by letters, digits or hyphens,
up to 32 characters. Names cannot be changed after creation.

A saved app starts disconnected. Connecting verifies its provider identity and
saves a reference to encrypted credentials. Add profiles and a launcher when
provider events should start agents; an app used only for tools needs no launcher.
There is no separate connection object to create or share. Two apps configured
with the same bot remain independent setups, with separate credential updates
and lifecycle. Avoid overlapping launchers for the same conversation: duplicate
menus, agents or replies are possible.

The detail page shows setup state, launch settings and available capabilities.
Changing offered profiles affects future launches. Disconnecting stops provider
access; deleting also releases the app's credential reference. Neither action
removes agents, their history, or messages already posted in the provider. Agents
remain usable through the dashboard and API.

## Select capabilities independently

An app can supply tools, named listeners and one interaction handler. Configs
choose each independently. A tool lets the model act; a listener delivers incoming
messages; a handler presents questions and approvals outside the dashboard.
The launcher is separate: it decides whether and how to start agents.

For example, after creating a GitHub app named `reviews` and a Slack app named
`engineering`, this config reads one PR and permits approvals in a Slack channel:

```yaml
instruction: Review the PR. Select engineering as your interaction handler before requesting approval.
model:
  provider_config: my-provider
  name: my-model
tools:
  ask_question: {}
  app__reviews__read:
    config: {repository_id: 123456, pull_request: 42}
interaction_handlers:
  engineering:
    config: {channel_id: C123}
```

Tools use `app__<app-name>__<operation>`, with one entry per app and operation.
Their optional `config` contains fixed
implementation settings; it is separate from model arguments. With empty config,
the model supplies the destination. Fixed destination fields disappear from its
argument schema and cannot be overridden. The tool description explains the
fixed destination. The app's credential permissions remain the provider access
boundary; Omnara also checks project ownership, current app status and ordinary
[tool permission](/tools/permissions).

Names are resolved to immutable app IDs when the config is compiled. Deleting an
app and reusing its name does not redirect old agents. Re-save profiles that should
use the replacement app before their launchers run; old pinned references are not
automatically rebound. Credentials are loaded
live, so rotation does not require rewriting configs. A pending tool call cannot
silently acquire a different app, fixed config or permission after a config change.

## Listen now or follow a conversation later

Listeners use `<app-name>__<listener-name>`. For example:

```yaml
tools:
  app__engineering__post_message:
    config: {channel_id: C123}
listeners:
  engineering__thread_messages:
    config:
      conversations:
        - {channel_id: C123, thread_ts: "111.222333"}
```

Saving this config does not subscribe anything. Activating it for an agent creates
its initial subscriptions. The sending tool is independent: removing or denying
it leaves those subscriptions intact.

An empty listener config creates no initial subscriptions, but permits runtime
following. A Slack or Discord post with `follow_replies: true` registers the
confirmed conversation under the matching configured listener. This supports a
scheduled agent that posts an update and then receives replies in its new thread.
Removing the listener stops both initial and runtime subscriptions. Re-adding it
does not resurrect old follows, and a sending tool cannot recreate a missing listener.

## Launch from provider events

[Slack](/integrations/slack) and [Discord](/integrations/discord) create thread
agents from mentions. With one offered profile, the agent starts immediately.
With several profiles, the bot presents a selection menu and starts only the
chosen profile. [GitHub](/integrations/github) can start work from a PR mention
or PR creation; its launcher runs each configured slot.

A profile launch derives a config with the app's tools, listener and supported
interaction handler for that conversation. The profile stays unchanged. Existing
explicit entries win as complete entries, including disabled tools and different
fixed destinations. The launcher adds missing entries only. An existing-agent
launcher slot forwards input without adding capabilities.

The create-agent API also accepts `tools`, `listeners` and `interaction_handlers`
when deriving a config from a pinned config or profile. Config authoring and app
management require project management permission. App credential setup requires a
user session or personal access token; organization API keys can perform ordinary
runtime work. App capabilities and runtime subscriptions are not inherited by subagents.

Ordinary model output stays in Omnara. Posting externally requires an app tool.

## Route questions and approvals

Tool-capable configs include `list_interaction_handlers` and
`set_interaction_handler` by default, unless explicitly disabled. The list is
paginated and returns each handler's description and effective argument schema,
plus the current selection independently of the page. The model selects a handler
and destination arguments, or uses `{"handler": null, "args": {}}` for dashboard only.

An empty handler config lets the model choose a destination accessible to the app.
Fixed config, such as a channel or thread, restricts that choice. Anyone able to
respond in the selected provider conversation can answer its questions and
approvals; they do not need an Omnara account. Choose a destination whose audience
you trust to make those decisions.

A newly accepted provider input selects a unique matching handler for future
interactions. No matching handler means dashboard only; an input without a
provider origin preserves the selection. Each interaction captures its destination
when created, so changing the selection does not move an existing prompt.

The dashboard remains available if provider presentation fails. Removing a handler,
disconnecting its app, or changing its fixed config invalidates old external
callbacks. See [interactions](/events/interactions) for answering through the API.

For an existing Slack deployment, use the coordinated
[maintenance cutover](/self-hosting/composable-apps-cutover). Self-hosted operators
can inspect, retry or discard failed inbound receipts with the
[recovery commands](/self-hosting/composable-apps-cutover#recover-failed-app-events).
