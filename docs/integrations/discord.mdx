Create an Omnara app named, for example, `support` with definition
`omnara.discord`. It owns the Discord credentials and optional launcher. Select
tools and the interaction handler in agent configs, and attach
conversations with app-owned subscriptions; see [Apps](/integrations/apps).

## Connect your bot

Create an application and bot in the [Discord Developer Portal](https://discord.com/developers/applications).
Record the Application ID, separate bot User ID, bot token and public key. Enable
Message Content Intent. Omnara receives guild messages through Gateway; this
app does not support DMs. Install the bot in your server with permission to read
history, send messages, create public threads and send in threads. Grant Attach
Files if agents will upload files.

Save the token as a project-available [generic secret](/organization/secrets),
with `material: {"kind":"generic","value":"your-bot-token"}`. Configure the
saved app through `POST /orgs/{orgID}/projects/{projectID}/apps/{appID}/setup`:

```json
{
  "expected_setup_revision": 1,
  "provider_tenant_id": "111111111111111111",
  "provider_account_ref": "222222222222222222",
  "credential_secret_id": "sec_aeaqcaibaeaqcaibaeaqcaibae",
  "provider_config": {"shard_count": 1, "public_key": "YOUR_64_CHARACTER_HEX_PUBLIC_KEY"}
}
```

Use the app's current `setup_revision`. `provider_tenant_id` is the Application
ID and `provider_account_ref` is the bot User ID; neither is the guild ID. Setup
verifies those identities with Discord. Keep one shard unless the bot requires a
larger topology. Omit `provider_config` during token rotation to keep the current
settings. Supplying it replaces the settings, so include every field you intend to retain.
The public key verifies callbacks; it is not the bot token.

Each saved app has an independent runtime. Apps can use the same bot credentials,
including in different projects, but duplicated sessions consume provider capacity.
Overlapping launch behavior can create duplicate responses. Omnara does not merge
these independently configured apps.

## Launch from mentions

Choose profiles and a channel scope in the app's settings. A mention in the
parent channel creates or reuses the public thread attached to that message. A
mention already inside a thread uses that thread. One offered profile starts
immediately; several profiles produce a menu and start only the selected profile.
Anyone in the conversation can choose. The menu expires after an hour; send
follow-ups after selecting, because earlier replies may be missed.

The launcher derives the agent's tools and interaction handler for the thread,
preserving existing explicit entries in the profile config, and attaches a thread
subscription. Human messages
steer the agent and cancel open interactions. Bot and webhook messages are ignored.
Edit the offered profiles to change future launches; existing agents keep their configs.

## Scheduled threads

Use **Add schedule** on the app page to post a template opening message and launch
one profile in its new thread. The tools, reply subscription and interaction handler
are ready when the agent starts. Schedules can coexist with mention launches.
See [scheduled app launches](/integrations/apps#start-a-new-thread-on-a-schedule)
for setup, template variables and recovery behavior.

## Select capabilities manually

```yaml
tools:
  app__support__read: {}
  app__support__post_message: {}
```

`read` supports `before` and `limit`. `post_message` takes `content` and up to 10
`artifact_ids`. Without app-agent context, supply `channel_id` and optional
`thread_id` on every call. A provider or scheduled launch binds the tools to the
launch conversation: omitted destination fields use that context. A server channel
context permits child threads in that channel; a thread context stays confined to
that thread. Destinations outside the context are rejected. The static schema
always includes destination arguments.
Optional `guild_id` is verified against Discord before sending; the indexed
conversation context does not store guild metadata.

A confirmed post with `follow_replies: true` adds an app-owned subscription to its
conversation. For an immediate subscription, send this body to the
[app subscriptions API](/integrations/apps#subscribe-a-conversation):

```json
{
  "agent_id": "YOUR_AGENT_ID",
  "type": "thread_messages",
  "conversation": {
    "guild_id": "333333333333333333",
    "channel_id": "444444444444444444",
    "thread_id": "555555555555555555"
  }
}
```

The default event is `message`. Omit `thread_id` for a channel subscription;
channel-root intake requires a bot mention. Removing the sending tool or changing
config does not remove subscriptions. Use **Stop forwarding** on the app page or
DELETE the subscription to remove it, including while the app is disconnected.

## Questions, approvals and profile menus

Configure the app's public key, then set the Discord registration's
**Interactions Endpoint URL** to:

```text
https://YOUR_OMNARA_HOST/api/integrations/discord/APPLICATION_ID/interactions
```

Use the numeric Discord Application ID, not Omnara's `app_…` ID. One public
endpoint can verify callbacks for independently configured apps. Each menu or
agent interaction captures its owning app, so its answer is routed only there.
Require successful [signed PING verification](https://docs.discord.com/developers/interactions/receiving-and-responding)
before offering profile menus or external approvals.

Select `interaction_handlers: {support: {}}` in an agent config to expose the
handler. The model chooses it with `set_interaction_handler`, supplying a complete
`channel_id` and optional `thread_id` and `guild_id` in `args`. Sending context does
not restrict this selection. Incoming provider input automatically selects the
full origin address, including on launch. Questions remain answerable in the dashboard if Discord
presentation fails. There is no Gateway fallback for interaction answers or
automatic slash-command registration. A bot used only for messages with one
profile can omit the public key.

## Restarts and deployments

A worker saves its Discord session and last committed event sequence in Postgres.
The event receipt and sequence are saved together. When another worker takes over,
it resumes that session and Discord can replay missed events; repeated message
receipts are deduplicated. A database lease prevents two workers from committing
for the same saved app and shard. Normal shutdown releases that lease; after a
crash, a replacement waits for it to expire, normally within 30 seconds.

Keep replacement workers healthy during routine deployments, and allow the old
workers to shut down gracefully. Postgres and Redis must remain available. Discord
retains replay history for a limited time: a long outage or an invalidated session
can still leave a gap. The worker records that it must start a fresh session;
restarting is not a guarantee that Discord retains every missed message.

HTTP interactions use the API service separately. Keep a healthy API instance
receiving requests while another drains. Routine rolling restarts differ from
this release's [one-time migration maintenance window](/self-hosting/composable-apps-cutover).

Before a production rollout, use a dedicated test guild to check a mention,
a plain reply in the resulting thread, and another reply after restarting the
test worker. Confirm that they reach the same agent without duplicate inputs.
Also verify a signed interaction callback if using approvals or profile menus.
The automated suite uses local provider fixtures; it does not replace this live
check of the bot's intents and guild permissions.
