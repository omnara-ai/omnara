## Project apps for Slack, Discord and GitHub

Create an app from your project's Apps page and configure its provider setup and
launch behavior. Slack and Discord can start a thread agent from a mention and
offer a profile menu. GitHub can launch from a PR mention or opening a PR, then
read and write discussion and inline comments. Tools, listeners and interaction
handlers can also be selected independently in agent configs.

This release replaces native Slack setup with project-owned apps. Tool names now
include the app name, such as `app__engineering__post_message`; listener and
interaction-handler configs refer to that app as well. Existing Slack data and
configs are migrated during a coordinated maintenance window. Open Slack prompts
are canceled, while agents, conversation history and provider messages remain.
Self-hosted operators must follow the [cutover playbook](/self-hosting/composable-apps-cutover),
including draining work and stopping cluster writers before migration.

The public setup API now creates an app before verifying its credentials. Update
clients using the old integration setup or destination APIs together with the
cluster release. Customer-hosted integrations continue to use ordinary agent
inputs, custom tools and interaction APIs. See [Apps](/integrations/apps).

</Update>

## Agents can now delegate to subagents

Declare subagents in a config and an agent can spin up helpers, hand each one a task, and collect their results in a single conversation. Also new: deferred tool loading, usage and cost pages, large tool results as files, and custom model endpoints in the dashboard.

### Subagents

Add a `subagents` block to an agent's config and it gains tools to spawn helpers, send them messages, read their progress, and stop them. A subagent launches from another profile or from a copy of the parent's own config, starts with a clean context, and shares the parent's machines. Its final answer arrives back in the parent's conversation. You set how many can run at once and how deep they can nest, and they appear in the dashboard and API as agents with a parent. See [Subagents](/agents/configuration#subagents).

### Deferred tools and tool search

Mark any tool `deferred: true` to keep its definition out of the model's context until it's needed. The model calls `tool_search` to load matching tools on demand, which keeps prompts small and the provider's prompt cache intact for agents with large MCP tool sets. See [Deferred tools](/agents/configuration#deferred-tools).

### Usage and cost

New usage pages for your organization, projects, profiles, and agents show model API usage, and the model catalog now lists pricing per million input and output tokens.

### Large results become files

Tool results over 50 KiB are saved as files instead of filling the conversation. The agent gets a preview and can page through or search the full result with the new `read_file` and `search_files` tools, with no machine required. The transfer tools are now `upload_file` and `download_file` and work with paths under `/artifacts`; existing configs were migrated automatically. See [Built-in tools](/tools/built-in).

### Dashboard

Add a model provider with a custom base URL and API format (OpenAI Responses, OpenAI Chat Completions, or Anthropic Messages) from the Add provider dialog, for proxies and self-hosted servers such as LiteLLM, vLLM, or Ollama. Open an agent's raw event log from its conversation, and get a warning before leaving unsaved agent or profile edits.

### Reliability and API notes

Daemon crashes on connected machines now back off instead of restarting in a tight loop, and failure reports capture the crash output. Dependency updates resolved all open high-severity advisories. For API users: machine tools and bindings now use public machine IDs (`mch_...`) and the per-agent `machine_ref` field was removed from responses.

</Update>

## Omnara is now available over MCP

MCP joins the API, SDK, and CLI as a way to work with Omnara. Connect Claude Code, Cursor, or any MCP client to the Omnara API and spin up Omnara agents from another agent. Also new: Modal sandboxes, Amazon Bedrock with AWS credentials, and in-place secret editing.

### Connect an MCP client

Add `https://app.omnara.com/mcp` to any MCP client. For example, with Claude Code:

```bash Claude Code
claude mcp add --transport http omnara https://app.omnara.com/mcp
```

Or with Codex:

```bash Codex
codex mcp add omnara --url https://app.omnara.com/mcp
```

Sign in through the browser on first use; there are no tokens to paste. Your agent can then launch Omnara agents, send them messages, follow their progress, and manage profiles, secrets, and machines, with the same permissions you have in the dashboard. Omnara is also listed in the official MCP Registry as `com.omnara/omnara`. See [Connecting MCP clients](/api/authentication#connecting-mcp-clients).

### Modal sandboxes

Bring your Modal account as a sandbox provider alongside Blaxel, Unikraft Cloud, and Daytona. Create a pool with your Modal token and choose the image, region, and resource limits. See [Machine pools](/machines/pools).

### Amazon Bedrock with AWS credentials

Bedrock model providers can authenticate with AWS credentials instead of an API key, including assuming a role. They use the same AWS credential secrets as SigV4 MCP servers. See [Model providers](/organization/model-providers).

### Edit secrets in place

Rename a secret or replace its value from the dashboard. Agent configs that reference it keep working. See [Secrets](/organization/secrets).

### Reliability

Agents that reach a model's output limit now continue their answer instead of stopping short. You can set idle and total timeouts for provider requests. Commands waiting on a machine that looks online but isn't responding are released after five minutes so the agent can move on.

</Update>

## Introducing Omnara

On September 2, we relaunched Omnara as the open-source alternative to Claude Managed Agents. Run agents for yourself or your team, or build them into your product through the API. Omnara handles durable execution, sandboxes, and conversation history while you choose how each agent works. Here’s what we’ve shipped so far.

### Agents that pick up where they left off

Agents keep their conversation history across crashes, restarts, and machine disconnects, so work can resume without starting a new conversation. Set one up in the dashboard or with a small [configuration file](/agents/configuration). Save that setup as a profile to reuse it whenever you need a new agent.

### Choose your models and machines

Use models from OpenAI, Anthropic, OpenRouter, or Amazon Bedrock, or connect a compatible model you host yourself. You can choose the [model](/organization/model-providers) that fits each agent's work.

When an agent needs to run commands, it can use an Omnara-managed sandbox or a [machine you connect](/machines/overview), such as a laptop or server. You can also bring your own Blaxel, Unikraft Cloud, or Daytona account. Agents can create sandboxes when they need them and release them when the work is done.

### Connect tools and share skills

Agents can search the web, run commands, and work with files using built-in tools. Connect [MCP servers](/tools/mcp) to give them access to your services and data, or add custom tools for actions in your own application. You can browse available MCP servers and their tools in the dashboard.

[Skills](/tools/skills) let you package instructions and supporting files for work your agents do regularly. Upload and edit them in the dashboard, then reuse them across agents and projects.

### Work with agents as they run

Follow an agent's progress live, send a correction while it's working, or queue up its next task. You can decide which [actions need approval](/tools/permissions), and agents can pause to ask questions when they need your input.

You can also attach images and documents to a conversation. Agents can return reports, spreadsheets, and other files for you to view or download.

### Slack and scheduled work

Connect an agent profile to [Slack](/integrations/slack) so your team can work with it in threads and DMs. Each conversation keeps its own history, and people can answer questions, approve actions, and receive files directly in Slack.

For recurring work, schedules can start a new agent or send a task to an existing one. We've included [examples](/examples/overview) that collect updates from X, Reddit, LinkedIn, and PostHog and deliver a digest to Slack.

### Build agents into your product

The [REST API](/api/overview), TypeScript SDK, and CLI let you launch agents, send messages, follow their progress, and respond to requests for input. You can build these interactions into your own application or work with agents from your terminal.

For teams, projects and roles control who can manage or use agents and shared resources. Store credentials as secrets and choose which projects can access your models, machines, and skills.

Get started on [Omnara Cloud](https://app.omnara.com) or [self-host](/self-hosting/deployment) on your own infrastructure. Omnara is open source under Apache 2.0. The [quickstart](/quickstart) walks through launching your first agent.
